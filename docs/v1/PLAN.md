## 1. 不可变约束（贯穿所有 Unit）

- Outer = 整张物理相纸外缘，含完整白框；Inner = 成像区。二者独立保存、编辑。不得把画面边缘当成相纸外缘。
- 原始扫描只读。任何影响外部文件的操作单独说明并确认。
- 真实扫描边框与生成边框是两个独立模式，不得静默互换。
- 800–1600 DPI、8/16-bit TIFF 工作流的画质、色彩管理、完整边框和几何正确性不因性能优化受损。
- 保留无 Qt 的可移植核心和稳定项目格式；本轮不发布移动端。
- 未提及的现有功能全部保留（[FEATURE-FREEZE.md](FEATURE-FREEZE.md) 是回归基线）；确需改动先写影响说明并取得确认。
- PhotoFrame（边框效果）、SpektraLab（界面与工程规范）是既定参考；Lightroom / 像素蛋糕截图只用于指定交互，不复制品牌、图标或受保护素材。

## 2. 审核意见的落实（12 条）

| # | 审核要求 | 落实方式 |
| --- | --- | --- |
| 1 | Stage A 不等 D1–D8 | 版本登记、复现、失败回归测试、功能清单、RFC 立即进行；缺设备/外部软件/大文件登记为对应测试的阻塞，不阻塞无关开发。 |
| 2 | 合并前提供测试包 | 每个 Unit：PR → 自动测试 → **绑定 PR head 提交的测试包**（版本、完整 SHA、构建号、SHA-256、BUILDINFO.txt）→ 自测及必要的用户验收 → 合并 → 对合并结果打 Tag、发布并校验发布包（§6）。 |
| 3 | 自动保存不直接取代手动保存 | 保留手动保存；新增**恢复快照**（未提交编辑的崩溃恢复）与**历史备份**，三者分开存放、分开说明。改为图库自动提交须另提“保存语义 RFC”（放弃修改、保存失败、只读目录、磁盘满、异常退出），获确认后才实施。同一图库内“图库／修改照片”切换只是切换视图，不保存、不重载、不取消任务；只有真正替换当前工程或图库时才执行统一的数据保护流程。 |
| 4 | `.fklibrary` 只是待评审方案 | 图库存储 RFC 必须覆盖：数据格式与 schema 版本；原子写入、备份轮换、恢复顺序；同一图库被两个进程打开；旧工程迁移预检与失败回滚；新版本工程被旧版本打开时只读；原图移动后的重新定位与跨平台路径；缓存可删可重建、不得存放唯一的关联数据。旧 `.fkproj` 一律“迁移副本”，原文件保持可用，绝不静默原地升级。 |
| 5 | 回导不能“第一个命中就用” | 证据模型：先确定目标相纸 → 再确定导出版本 → 最后验证几何、方向、色彩、内容是否兼容。嵌入 ID、内部记录、文件名、内容签名都只是证据；证据冲突必须提示；文件名或相似度不能覆盖更强的冲突证据。选定目标后的手动回导允许任意文件名、无元数据、无侧车，但仍做安全校验和预览确认。 |
| 6 | 旋转、缩放、裁切分开 | 方形/低纹理/对称画面方向不可靠时允许人工指定；单纯缩放与外部裁切是不同变换；裁切后缺失的图像不静默拉伸填满 Inner；保存最终确认的变换及对应导出版本，预览与输出用同一份结果；画布缩放、显示旋转与导出变换互不混用。 |
| 7 | “仅画面”默认拉直须明示 | 默认使用明确标注的拉直模式，导出前显示是否重采样；保留像素裁切；依据实际几何（任意四边形需要透视变换）而不是只看旋转角；输出尺寸、插值方式、回导所需变换写入内部导出记录。 |
| 8 | 不绝对化“未修改往返不再 bit-exact” | 自然融合与档案精确模式分别验收；0.03 mm / 0.02 mm 只是起点，不默认叠加，不提前当最终参数。“Inner 外像素不变”限定在相同输出色彩空间、位深和可直接比较的几何条件下；有全局色彩转换或拉直重采样时，验证边框未被局部调色替换或污染。“逐像素一致”≠ 文件字节相同。 |
| 9 | 不直接决定拒绝 DNG 回导 | 在 U001 冻结格式能力矩阵（[FORMAT-MATRIX.md](FORMAT-MATRIX.md)），列导出格式、可读软件、回导子类型、位深/ICC/透明度限制、已验证/未验证/不支持；DNG 回导范围在 FK-012 Unit 按能力、成本、既有承诺评审，不删减已有能力，也不扩展成 RAW 解码。 |
| 10 | 异步安全提前打基础 | U002（最小任务安全框架：工程/相纸/版本/参数快照、代次校验、取消、失败状态）在所有回导/预览/恢复 Unit 之前完成；失效任务既不能更新画布，也不能回写工程记录、覆盖最终输出或把失败显示成成功。全面缓存预算与性能优化在 U017。 |
| 11 | 内存与指纹要可执行 | 统一预算覆盖解码、变换、合成、编码缓冲，不只缓存；任务启动前预留内存、限制并发与等待队列；大图按需/分块/流式；指纹流式计算、不整体读入、不在 UI 线程计算完整哈希；校验与实际读取之间文件改变必须失效重验；测量方法写明硬件、输入规格、峰值内存、取消响应、批次结束后稳定内存。既有内存数字是目标，需基线实测与可行性评审，不为达标静默降质。 |
| 12 | 证据与追踪 | 截图推断的原因标为“待验证假设”，确认后附源码位置或复现证据（WORKLOG 2026-10-30 已按此记录）；真实扫描分**调参集**与**独立回归集**；真值标注记录尺寸、DPI 可信度、坐标约定、版本、边缘不确定区；原图、路径及可关联用户的信息未经单独确认不入库，坐标文件先审内容；SpektraLab 开发规范逐条对照（[PROCESS-CHECKLIST.md](PROCESS-CHECKLIST.md)）；26 项需求 → 实现、提交、测试、证据的追踪表（[TRACEABILITY.md](TRACEABILITY.md)）。 |

D1–D8 的处理（按审核建议）：D1 0.5.0 作为冻结基线以明确标注限制的预发布发布，与 CI 修复分开决定；D2 暂不改为自动保存；D3 默认目录用系统接口取得、用户可改、不硬编码；D4 接受明确标注的拉直；D5 自然融合方向可行，参数待真实样本；D6 先交格式矩阵；D7 真值先本地标注，入库须单独确认，测试集与调参集分开；D8 可用设备未明确前，相关项列为待验收。

## 3. 关键设计方向（各自的 RFC 在实现它的 Unit 开始时写出并评审）

1. **数据模型**：图库沿用并演进现有工程模型（不另造一套丢历史的系统）。导出记录（几何快照、方向、ICC、位深、指纹、插值、输出尺寸）进入工程/图库内部；`.fk.json` 侧车改为可选。schema 变更走“迁移副本”。
2. **坐标**：扫描原图坐标是唯一稳定参考；整图旋转、显示变换、导出坐标、回导对齐分别记录、可组合，禁止反复重采样。
3. **回导证据模型**：目标 → 导出版本 → 兼容性验证 → 预览确认；歧义必选、冲突必示。
4. **任务安全**：每个结果绑定 project/item/purpose/generation 与参数快照，失效即丢弃并释放。
5. **数据保护**：手动保存 + 恢复快照 + 历史备份；统一“替换当前工程”入口。

## 4. 开发方式：按 Unit 开发、验证、发布

Unit = 可独立验收的交付单元（[UNITS.md](UNITS.md)）。每个 Unit：

1. 确定范围、明确不包含的内容、依赖和验收条件（写入 UNITS.md）；涉及新模块/接口先写 RFC，新功能先写 PRD。
2. 从最新 `main` 建任务分支 `unit/Unnn-<名称>`；实现并补充回归测试（修复类：先有失败测试）。
3. 更新 `VERSION`、`docs/release-notes/v<版本>.md`、USER-GUIDE、TRACEABILITY、WORKLOG。
4. 建 PR；CI（Linux/macOS/Windows 核心 + 应用自检）全绿；Release 工作流为 PR head 提交构建测试包并做打包冒烟测试（版本/提交一致性检查）。
5. 开发者自测（含真实扫描场景，若相关）；在 PR 中写测试说明与实际结果。
6. 满足合并条件后合并（仓库保护或审批要求不允许自动合并时，请所有者合并；不绕过）。
7. 在 `main` 上手动运行 Release（publish）：在合并提交上建唯一 Tag `v<版本>`，生成并校验发布包，建 GitHub Pre-release。
8. 更新 UNITS.md、TRACEABILITY.md、WORKLOG.md，继续下一个 Unit。

问题修复：记录出现版本与复现步骤 → 按版本差异和相关 Unit 定位（必要时比较历史版本或二分提交）→ 从最新集成基线建修复分支 → 补该 Unit 及受影响依赖的回归测试 → 发布新版本并注明修复的 Unit 与受影响旧版本。不回退到旧 Unit 代码上开发，不移动旧 Tag，不覆盖旧包。

### 版本编号

- 基线：`v0.5.0`（冻结基线，预发布）。
- Stage B（正确性与保护）：`v0.6.0-alpha.N`；Stage C（检测与编辑）：`v0.7.0-alpha.N`；Stage D（图库与布局）：`v0.8.0-alpha.N`；功能完成后 `v0.9.0-beta.N`；正式发布前 `v1.0.0-rc.N`。
- 只有满足全部正式发布门槛（§7）才发布 `v1.0.0`；任务数完成不等于 v1.0 验收通过。
- Release 标题：`v<版本> | U<nnn> | <工单> <简述>`，例如 `v0.6.0-alpha.2 | U002 | FK-006 任务安全框架`。

## 5. 每个 Release 必须包含

本次及累计已完成功能；Unit ID、关联工单、PR、完整提交 SHA；Windows/macOS 分发包及 SHA-256；可执行的测试步骤与实际结果；与上一版本的比较链接；已知问题、未验证内容与平台差异；工程格式变化、迁移和回退限制。软件内版本（关于对话框、`--version`、自检报告）、构建信息、分发包（BUILDINFO.txt）、Tag、Release 必须一致；发布工作流自动检查打包后应用报告的版本与提交。某平台未构建或未验证必须明确标注；源码更新、按钮出现或 CI 绿灯都不算完成交付。

## 6. 测试与证据

- **自动**：核心 GoogleTest（Linux/macOS/Windows）、检测评估语料、应用离屏自检（真实控制器 + 截图）、打包后冒烟测试。
- **已知问题测试**：Stage A 确认的缺陷各有一个“修复前失败”的测试（核心用 ctest `WILL_FAIL`，应用自检用 known-issue 检查）。缺陷存在时 CI 绿；一旦不再复现，CI 变红，修复它的 Unit 把它改为常规测试——修复前失败、修复后通过都有记录。
- **真实扫描**：调参集与独立回归集分开（[REAL-SCAN-GT.md](REAL-SCAN-GT.md)）；原图不入库。
- **真实桌面、外部软件、8/16 GB 设备、干净系统安装**：需要人工或真实硬件，结果按实际记录；未执行的记为“待验证/阻塞”，不计通过。
- 测试报告分开统计：通过、失败、跳过、未启动、阻塞、已知问题。

## 7. v1.0.0 发布门槛

无未关闭的 P1；无无法完成的核心流程；无误导性成功提示；无“有控件无实现”；P2 中明确要求的功能已完成或有书面范围调整；26 项逐项有实现、提交、测试与证据；真实扫描 GT 结果、外部软件往返记录、真实窗口截图与 8/16 GB 性能结果齐全（缺失项须书面确认后才能发布）；中文使用指南经非开发者按指南完成一次四张相纸完整往返。
